# Architecture

The React entry point renders `AuthProvider`, which restores a cookie session before showing `AppShell`. Sign-in and mandatory password changes gate the Coach. `AppShell` exposes Team access only to admins; `CommerceCoachPage` exposes Learning to reviewers/admins. `src/auth/client.ts` attaches the CSRF token and handles revoked/expired sessions. UI visibility improves usability; Express and PostgreSQL enforce authorization independently.

Express serves the frontend and authenticated `/api` routes. `/api/auth/login` and a minimal health endpoint are public. Authenticated `/api/auth/me`, logout, and password-change routes remain available to accounts required to change a temporary password; other APIs require completed password setup. `/api/users` requires admin; organization feedback review requires reviewer/admin. AI credentials remain server-only.

`server/db.ts` uses a restricted data login belonging to `coach_app` and a separate authentication pool belonging to `coach_auth`. Only the authentication pool can look up password hashes and create sessions; it cannot directly read feedback. Startup refuses ownership, superuser, CREATEROLE, BYPASSRLS, elevated memberships, and missing/disabled RLS. Each private-data operation uses one pooled connection and a transaction-local session hash. Commit/rollback clears context before connection reuse. The migration-owner connection is used only by offline administrative commands, not by web handlers.

`coach_private` holds organizations, per-organization user accounts, and hashed sessions. The runtime role has no direct table access. Narrow SECURITY DEFINER functions with fixed search paths expose authentication and organization-scoped administration. `coach_actor()` validates session existence/expiry and current account status on each operation. Password hashing is performed by Node’s asynchronous scrypt implementation; hashes, sessions, and role assertions never come from browser-controlled authorization headers.

`public.coach_feedback` has ENABLE/FORCE ROW LEVEL SECURITY. Members see only their own rows. Reviewers/admins see their organization’s rows. Inserts must match the actor’s organization/user, while a trigger prevents ownership changes and non-reviewer approval. No runtime DELETE/TRUNCATE/schema privileges are granted. Organization and user identity is derived from the stored session, not from configurable tenant/role strings. Auth-table access uses scoped database functions instead of exposing credential rows to SQL clients.

Password changes, role changes, account disabling, and password resets revoke sessions. User changes serialize on the organization to preserve the last active admin. Login session creation locks the user row to serialize against credential changes. Sessions expire after 12 hours; cookies are HttpOnly/SameSite=Strict and Secure in production; write APIs validate CSRF and origin. There is no public signup, email reset, or MFA. Optional Google OpenID Connect uses server-side code exchange, PKCE, nonce, and a single-use browser-bound state stored in private PostgreSQL tables. Migration 002 adds Google subjects and session authentication methods. Only coach_auth can consume flows or mint Google sessions. Existing active accounts link by Google-authoritative verified email once, then use the stable subject within their organization; roles and RLS are unchanged.

Coach chat uses authenticated retrieval and server-side OpenRouter/Gemini generation for every question. The latest message and up to 30 conversation messages reach the model; persisted mode flags and keyword workflow matches never select a response. Shared documentation, workflows, tools, and embedding snapshots are reference material. Both providers use `server/coach/systemPrompt.ts` to answer from the current step and identify documentation gaps. Screenshot search returns candidates; the model selects exact images with `suggest_screenshots`. The client validates those references without adding a keyword-selected guide. Empty or failed generation tries another configured provider, then returns an explicit error instead of a local product answer. Conversations and feedback persist in PostgreSQL under their respective RLS policies.

`server/migrations/001_security.sql` is idempotent and applied through `db:migrate`. SQLite is used only by the retained legacy schema tests and one-time import tool. Docker separates database, migration, and application services; PostgreSQL and embeddings use distinct named volumes.

Security references: [PostgreSQL RLS](https://www.postgresql.org/docs/17/ddl-rowsecurity.html), [SECURITY DEFINER precautions](https://www.postgresql.org/docs/17/sql-createfunction.html), [node-postgres transactions](https://node-postgres.com/features/transactions), [Node crypto](https://nodejs.org/api/crypto.html).

Conversation persistence: `/api/conversations` runs behind session/CSRF/readiness middleware. Migration 003 creates `coach_conversations` with forced owner-only RLS and restricted column updates. The API derives tenant/user from the session, stores JSON messages/state, and uses row locks with revision checks and idempotent retries. The frontend saves the question before generation and the reply afterward, restores timestamp objects on load, and prevents chat switching while saving or retrying unsaved data.


Before drafting, `server/coach/requestUnderstanding.ts` resolves the request, language, current step, subquestions, account-access needs, and focused search queries from up to 30 conversation turns. It searches the bundled documentation using those model-resolved queries. Existing client retrieval remains supplementary; raw-message matches must not override the resolved request. This is generated interpretation, not a keyword route or response template.

`server/coach/answerReview.ts` checks the generated answer against source evidence and conversation context, then runs a separate compact visual review. Both providers request structured outputs, and image filenames are locally validated against the canonical catalogue. The visual pass does not receive full articles or feature IDs. Drafting tools handle knowledge, training, quizzes, and domain lookup; final review owns image selection. Failed understanding falls back to direct generation from history. Failed answer review preserves the draft without images; failed visual review preserves the reviewed text without images. No account lookup or mutation tools were added.

The answer reviewer emits an internal evidence check for each subquestion before the merchant-facing answer. The visual reviewer maps canonical image IDs to numbered answer instructions; invalid IDs or instruction indices get one correction attempt. `providerRetry.ts` retries transient provider transport failures once, without repeating tool execution.
